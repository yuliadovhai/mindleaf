# ADR 0011: Тарифи для репетитора й оплата через LiqPay

- **Статус:** Прийнято, 2026-11-14
- **Пов'язане:** [PROJECT.md → «Тариф і оплата»](../../PROJECT.md#тариф-і-оплата-apibilling), [ADR 0008](0008-ai-grading-outside-the-vpc.md), `backend/app/services/billing.py`, `backend/app/services/liqpay.py`

## Контекст

Застосунком платить репетитор. ШІ-функції коштують грошей за кожен виклик, решта майже нічого не коштує. Обмеження архітектури ті самі: API Lambda без виходу в інтернет, жодних погодинних платежів за інфраструктуру.

Рішення власниці проєкту:

- тарифи «Безкоштовний» (до 3 активних учнів, без ШІ) і «Pro» за 199 грн на місяць або 1990 грн на рік;
- оплата через LiqPay, з автосписанням;
- коли Pro закінчився, а учнів понад ліміт, кабінет стає лише для перегляду.

## Рішення

1. **LiqPay, бо оплата не потребує мережі з боку API.** Форму підписки (`action = "subscribe"`) API підписує локально, а браузер сам відправляє її на `https://www.liqpay.ua/api/3/checkout`. Результат LiqPay надсилає на наш `server_url` (function URL, вхідний запит), і ми перевіряємо його підписом.
2. **Pro дає тільки перевірений callback.** Кожна оплата з новим `payment_id` подовжує `paid_until` на календарний місяць чи рік від `max(зараз, paid_until)`. Усі callback пишуться в `billing_events`, а унікальний індекс по `payment_id` разом зі статусом і перевірка «цей платіж уже враховано» не дають подовжити двічі.
3. **3 дні запасу** після `paid_until`, бо LiqPay повторює невдале списання протягом 72 годин.
4. **Обмеження через одне місце** (`billing.is_pro` і `plan_state`):
   - ліміт учнів дає `402 plan_limit`;
   - генерація тестів дає `402 pro_required`, а письмові відповіді йдуть репетитору замість ШІ;
   - режим «лише перегляд» дає `402 plan_read_only` на будь-які зміни репетитора, крім архівації учнів (щоб повернутися в ліміт), сторінки тарифу й профілю;
   - учні й батьки обмежень не помічають.
5. **Скасування** — запит сервер-сервер до LiqPay (`unsubscribe`). API його підписує, а ШІ-воркер поза VPC лише пересилає, не маючи ключа. Це працює навіть з вимкненим ШІ (`GRADER=off`).
6. **Підпис** — як в офіційних SDK: версія 3, `base64(SHA-1(key + data + key))`. Вхідні callback приймаються і з SHA3-256, бо поточна документація для версії 7 суперечить сама собі.
7. **Демо-режим** (локально, без ключів): своя сторінка «оплати» і `POST /api/billing/demo/pay`, що підписує callback демо-ключем і проганяє той самий обробник. В AWS без ключів оплата вимкнена, а не демо.

## Альтернативи

- **Monobank (plata by mono)** — рахунок створюється запитом до API банку. Для цього потрібен або вихід у інтернет з API, або ще одна черга через воркер, а користувач чекав би на оплату довше.
- **WayForPay** — схема схожа на LiqPay (підписана форма й повідомлення), але для тестів потрібен merchant-акаунт. Обрали LiqPay, бо в нього є sandbox.
- **Разові оплати без автосписання** — простіше, але репетитору доводилося б щоразу платити вручну.
- **Після Pro одразу «лише перегляд» для всіх** — жорсткіше, ніж треба. Хто вкладається в безкоштовний ліміт, працює далі.

## Наслідки

- Приватний ключ LiqPay лежить у змінних середовища Lambda — той самий компроміс, що й з паролем бази (ADR 0003).
- Локально справжній LiqPay не може надіслати callback на localhost, тож Pro через LiqPay працює лише в AWS. Локально — демо.
- Відкрите питання: чи приходить на кожне регулярне списання новий `payment_id` з тим самим `order_id`, і з яким алгоритмом LiqPay підписує callback. Перевірити першою sandbox-оплатою після деплою.
